# Experimental local Attendee meeting input

Adds a separate bar and recording-owned recognition pipeline for each participant UUID received from a locally operated Attendee bot. Microphone and shared-tab capture remain available. A guided Google Meet flow can explicitly create a bot and request entry. It does not return assistant audio to a call.

For clone → Compose → DSH entry, start with the concise [Google Meet quickstart](GOOGLE-MEET.md). This page covers technical setup, security and limits.

## Setup

1. Install plugin dependencies and build. The host uses the MIT-licensed `ws` dependency. Reload the plugin host after server changes: building alone does not update an already running DSH process.
2. Run Attendee locally and obtain a project API key. Only loopback API origins are accepted, without URL credentials, paths, queries or redirects. Save the key once in advanced Settings; it is bound to the exact normalized origin, never generic preferences or browser storage. The fixed host credential file is plaintext with mode 0600, not OS-encrypted storage, shared by authenticated browsers of this host. Metadata returns presence only, never the secret; protect the host account/files.
3. For plain-HTTP DSH on the same computer as Docker, include the packaged **DSH audio Compose override** below. It starts the audio bridge and provisions its deployment-local certificate automatically. No Mac proxy process, DSH HTTPS migration, public port, system certificate import or TLS-verification bypass is needed. DSH already using trusted HTTPS, or an explicit advanced WSS ingress, can still use the direct receiver.
4. Open **Settings → Live Voice → Conversation → Meeting mode**. Set the persisted **Default bot name**; advanced **Connection settings** owns API origin and key Save/Replace/Remove. Saving never starts reception or creates a bot. The password field is initially empty with a configured indicator, never a read-back secret. Blank input never deletes a key; removal requires confirmation and does not revoke current in-memory bot control or request departure.
5. Select Whisper HTTP, Qwen HTTP or a downloaded browser-local recognition model under Speech recognition. Native browser SpeechRecognition does not accept this PCM input. Keep the target conversation composer mounted while receiving; changing conversations closes reception to prevent cross-session delivery.
6. Click or right-click **Meeting mode** beside the composer and choose **Join Google Meet · experimental**. The quick form contains only the Google Meet URL and a text **Connect** action (or Enter). It uses the saved Settings name/key to prepare reception and request entry in one explicit operation, never on mount or menu opening. No name override, key field, configuration icon or local dialog remains in the composer. Missing configuration shows the Settings path. Obtain participant consent; admission may require the organizer. Per-participant 16 kHz PCM goes to the receiver with Attendee media recording disabled. Neither reception nor PCM proves admission; assistant audio is not returned. Shared-tab audio and its direct shortcut remain independent.
7. Participants discovered from the API appear under **Meeting participants** in the composer’s Google Meet panel even before they speak. Edit an individual name to set a connection-local alias for future transcript text; it does not rename anyone in the meeting or rewrite existing drafts. Independent composer audio bars appear when PCM arrives, with each participant name visible between the source icon and wave. Long names truncate without losing their full accessible label. New captures snapshot the provider, meeting-group ID, participant ID, original name and optional alias at capture start; renaming later does not relabel history. The debugger shows that source separately from custom session titles, identifies each segment/play action and exposes IDs to disambiguate duplicate names.
8. **Disconnect meeting** is the single active meeting action, without confirmation or a separate discard flow. It stops reception, resets local bot identity/control immediately and returns to URL + Connect. Remote departure and old-owner release are best-effort and time-bounded; failure produces a nonblocking warning, never a permanent released state that hides the form. You can connect again after the reset. Released/expired legacy identity without an owner resets locally without an API call. A local reset or departure request does not prove that the remote bot ended. Closing the panel or Escape performs no meeting operation. Saved Settings credentials and bot name are unchanged.

For HTTPS DSH, the receiver address is derived from the listener's attested origin, never browser-provided Host/Forwarded headers. For HTTP DSH, Connect discovers the Compose audio bridge at fixed loopback ports and opens a TLS-verified receiving connection. A missing bridge produces an actionable error, not an insecure WebSocket downgrade. **Advanced connection** permits an explicit WSS proxy URL. The guided URL/Connect flow does not attach an existing bot ID; it uses the saved origin/key to prepare reception and request a new bot explicitly. A container's localhost refers to that container, not the Mac; automatic HTTPS address discovery does not prove container reachability or certificate trust. Existing bots must already have the correct WebSocket destination; Attendee does not support updating it through PATCH. The secret receiver token is never displayed or stored in preferences.

## Compose-managed local audio

The plugin ships `deploy/attendee/compose.dsh-audio.yaml` and `audio_bridge.py`. Add the override last to your existing Attendee Compose invocation. In this development checkout, from the Attendee directory:

```sh
docker compose -f dev.docker-compose.yaml -f compose.arm64.yaml -f compose.fakecloud.yaml -f ../packages/live-voice/deploy/attendee/compose.dsh-audio.yaml up -d
```

For an installed plugin elsewhere, set `DSH_LIVE_VOICE_DEPLOY` to its absolute `deploy/attendee` directory and pass the override’s absolute path. The bridge reuses `attendee-local:arm64` by default; set `DSH_ATTENDEE_IMAGE` to your existing compatible Attendee image on other architectures. It uses the image’s existing Python `websockets==14.1` and `cryptography`, not an extra downloaded runtime. The override targets upstream development service names; custom deployments must adapt them explicitly.

Compose manages a one-shot certificate initializer and a bounded audio relay. Public certificate/root-bundle files live in one volume; the private key is in another and is never mounted into Attendee workers. The worker uses `SSL_CERT_FILE` with public roots plus the deployment-local certificate, preserving normal Meet HTTPS. The host obtains the certificate from a fixed loopback descriptor on port 18766 and trusts it only for this WSS connection to port 18765. Neither port offers arbitrary URLs, filesystem operations or a generic proxy. This bootstrap trusts the local machine/Docker deployment, **not hostile local processes** able to replace a loopback listener. Do not forward these ports. Certificate names, validity and chains are verified; no global Node or macOS trust is changed.

The relay validates the receiving host’s project key against the Attendee API before allocating one ephemeral session. It returns an internal `wss://dsh-audio-bridge:18765/ingest` URL with a fresh 256-bit producer capability. The plugin configures that URL on explicit bot creation. Audio stays inside Compose until the TLS-verified host connection receives it: no Docker-to-Mac hostname or incoming DSH port. Closing or losing the host receiver revokes the producer. The relay has no recording, replay or transcript storage. Recreating the worker to add the CA bundle can interrupt active bots; schedule this deployment change outside a meeting.

## Transport, identity and ownership

Attendee is the WebSocket **client**. The host accepts validated JSON PCM16LE and provides bounded, authenticated same-origin HTTP batches to the browser. A browser cannot listen as a WebSocket server. This initial browser relay polls every 100 ms; it is not a direct browser WebSocket connection or zero-latency stream.

Browser control/read routes use DSH Connection authentication plus an independent random owner capability. Ingress uses another 256-bit secret and rejects browser-Origin upgrades. One receiver, one bot-control lease, one ingress connection and 16 distinct participant UUIDs are allowed per host. Audio closes after 15 seconds without browser audio reads. Bot control is separate: a 10-second browser heartbeat renews a five-minute idle expiry, capped at two hours from connection creation. The host returns the current expiry timestamp. Audio stop never calls departure implicitly; late creation remains attached to its original control owner. An unresolved bot or uncertain creation blocks replacement until control is explicitly discarded or expires. Final plugin disposal and explicit control release revoke the capability and erase the in-memory API closure; neither proves departure, and a crashed page relies on expiry. The UI must confirm explicit discard, warn that the bot can remain in the meeting, and distinguish last-known bot identity/state from available control. Only create/leave API responses supply bot state; there is no upstream status polling or inferred joined/ended state from PCM. Reconnect is explicit, without replay or automatic capture after navigation.

Ingress limits: 128 KB JSON messages; at most one second of mono PCM16LE per packet at 8/16 kHz; 2 MB base64 or 1,500 queued packets. A complete participant snapshot is limited to 64,000 response bytes, five seconds, 16 cursor pages and 256 records; malformed or incomplete snapshots fail explicitly rather than publishing a truncated list. Malformed packets, overload, disconnect, ownership loss, API errors and recognition failure stop the receiver instead of silently dropping audio. No audio or transcript logging is added. **Proxy and Attendee logs may include the tokenized URL**: redact query strings and restrict logs. Never share the secret URL.

Names are fetched host-side from `GET /api/v1/bots/{bot_id}/participants`, matching `participant_uuid` to **uuid**, not API object ID or name. Unresolved names use localized participant numbers. Duplicate names and reconnection UUIDs remain separate sources. Shared Silero weights serve independent recurrent state; each participant has its own meter, segmentation, recorder and STT queue. Browser-local inference remains serialized without duplicate model weights.

## Recording retention

The configured count N keeps the newest N Attendee meeting groups by capture activity, including every participant capture and sparse burst while the group is retained. Active writers, pending writes and stars protect the whole group without consuming an ordinary slot. Silence between bursts neither proves call completion nor reserves a permanent slot: a newer meeting can expire an older quiet group, and resuming cannot recover expired history. Legacy microphone/shared recordings still keep N captures per source type. No upstream call-closed registry is inferred. Browser quota, storage eviction and explicit deletion can limit availability; retained or starred content is not a permanent archive guarantee.

## Important limits and validation status

- Attendee Meet skips all-zero frames. After 1.5 seconds of packet inactivity the adapter flushes and seals **only real received PCM**. Resuming packets start another capture burst once previous STT work settles. No recorded silence is fabricated. These burst recordings are not a continuous meeting archive; meeting-group retention applies while the group is retained, not continuous archival storage. Long pauses are not reconstructed sample-accurately.
- Timestamps are Attendee send-time wall clock, not proven media time. Transcript onset uses the first packet timestamp plus received sample offsets within a burst. Sparse frames, network batching and clock differences limit accuracy. Burst restart creates a new transcript block.
- **Per-participant messages do not prove overlapping voices are isolated.** The inspected Meet payload maps RTP contributing sources to users and chooses the loudest mapped contributor for a receiver frame. Real calls must verify independent tracks and preservation of simultaneous speech. The plugin cannot separate voices already mixed upstream. Teams is unvalidated.
- UUIDs identify bars and text. Updated display names affect future text, not existing drafts. Individual mute and input-policy controls persist across sparse capture bursts. Muting suppresses transcript delivery through the existing input policy; it does not stop the upstream bot, PCM transport or enabled audio recording. Cancellation rejects stale results; conversation changes stop reception. This source never plays its PCM through speakers.
- Automated tests cover validation, capabilities, bounds, separate PCM/VAD/STT state, names, teardown and stale results with simulated VAD/STT/storage. Real loopback WebSocket tests also cover token/Origin/duplicate-connection rejection, two participant PCM messages, revocation, and WSS certificate verification using an ephemeral certificate explicitly trusted only by the test client; an untrusted client is rejected. The Compose relay has isolated Python tests covering certificate/root-bundle reuse, untrusted-client rejection, key/Origin/token rejection, binary/oversize rejection, receive-only policy, PCM forwarding, duplicate producer refusal and revocation. A local HTTP fixture exercises the real API-key verifier with accepted/rejected credentials and confirms that redirects never forward the key. Concurrent verification is bounded to four requests. Node tests cover the TLS-verified relay consumer. `node scripts/test-attendee-relay.mjs` additionally runs the actual host consumer against the actual Python relay in a disposable container with ephemeral loopback ports: two UUID PCM packets arrive, and receiver cancellation revokes the producer. API admission uses a test key fixture, not production credentials or a real bot. The authenticated DSH control route was also verified after a host restart (capabilities/open/read/owner rejection/close), separately from these automated tests. The Compose bridge was subsequently deployed to the local stack: initializer exited successfully, bridge health passed, worker verified TLS 1.3 using its public CA bundle, and the current Node relay client authenticated with the real project API key, received the internal destination and closed cleanly. A Django development Host allowlist incompatibility was fixed by using the expected fixed localhost Host header for the fixed internal API request.
- A subsequent human-authorized authenticated GUI check joined a real Google Meet bot; the Attendee API reported `joined_recording`. Three named participant sources delivered PCM and displayed separate bars. Actual Silero inference and the configured Qwen HTTP recognition engine produced participant-labelled composer drafts. Recording was disabled and the drafts were not sent to DSH. Leave was requested through the GUI, and the Attendee API later reported `ended`. This validates that runtime path, not every recognition engine or acoustic isolation. Physical local-microphone capture and preservation of isolated simultaneous voices remain unverified. Overlapping timestamp buckets do not establish isolated simultaneous speech; the upstream loudest-contributor attribution and wall-clock timestamp limits above still apply.
- The GUI does not poll upstream meeting status periodically: admission can remain unconfirmed after the API reports `joined_recording`. Bot status in the GUI comes only from last-confirmed create/leave responses, not from receiver activity or PCM.
