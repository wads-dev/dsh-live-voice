# Conversation module

Transcription status separates detected speech (`recognizing`) from unsettled speech requests (`pendingTranscriptionRequests`, with legacy fallback to `pendingTranscriptions`). Aggregate `pendingTranscriptions` also includes storage/final-drain work for safety barriers; it must not be mistaken for visible transcription activity. `pendingDeliveryTranscriptions` isolates speech-boundary bookkeeping and queued/active speech work from silent recording writes, so automatic-send countdowns in either source cannot starve on periodic persistence. Cross-source delivery gates use the same distinction; missing fields retain conservative legacy blocking. Statuses are listening, listening and transcribing, waiting without speech, transcribing queued work without speech, and waiting for a command in Ignore mode. Playback remains separate; question and delivery countdown states retain their policy. Status copy has no ellipses. The compact recording indicator precedes the waveform and shows the committed audio frontier as seconds/minutes/unbounded hours, never wall-clock elapsed time; its saved-audio explanation is available only in the localized accessible name/tooltip.

Final recognition chunks join with a space. A confirmed paragraph boundary adds exactly two newlines; source changes also start a new block. Timestamp/source prefixes appear only at the first block, source change or paragraph. Recognition completion time and normal source activity/settings updates do not create timestamp boundaries. Composer text is append-only; user edits remain untouched.

Dictation is append-only at the current composer end. Final chunks preserve existing and manually edited text; provisional hypotheses never rewrite the editor. Client synchronization must accept a new manual publication even when the previous voice echo was skipped, while ignoring unchanged stale slot snapshots. Explicit Clear and normal submit actions are separate from dictation. Appends preserve the active caret, directional selection, focus and scroll; `app/client/composerSelection.ts` restores DOM bookmarks after the synchronous DSH editor write and publishes selectionchange through the editor bridge.

`models/chat.ts` interprets DSH chat turns and pending questions. `hooks/useConversationController.ts` subscribes to session state; `hooks/useConversationActions.ts` maps user actions onto the controller. `components/` renders composer controls, microphone state, playback controls, status, and waveform; `createConversationComponents.tsx` composes them for the application slot boundary.

Live Voice’s persisted `dshBusyEnterBehavior` is a user-reported fact about DSH, not a DSH configuration write. Delivery matching that behavior uses `inputActions.submit()`; the opposite uses the accelerated Ctrl+Enter gesture. Read the current answer at submission time for every delivery source; Queue is the compatibility default. DSH remains responsible for idle/unsupported-steering behavior.

Microphone and shared-input bars share `ConversationStatusBar` and separate `VoiceCoordinator` input-policy instances. `MeetingController.input()` adapts shared capture callbacks into that policy without owning duplicate playback. Per-source Ignore, commands, delivery mode, and timestamps remain independent. The application composer bridge cancels competing delivery intent on new accepted text and rearms an eligible source only when both inputs are idle and transcription is complete. Assistant playback and pending-question handling are delegated to the committed session controller.

Keep UI components session-facing rather than importing host engines or registering slots. Preserve the DSH composer contract: `useInput` provides subscribed input and `inputActions.setDraft()` updates the composer; a recognition result must not be lost to stale interim updates. History pagination must not count as a new user turn. The composer microphone toggle controls input mode only (`startConversation` / `stopConversationInput`), not speech-bar visibility or playback cancellation. Explicit Take microphone uses `takeMicrophone`; full End/disposal still releases all resources. The speech bar renders only actual caption text, leaving it empty before a segment is available and retaining the existing synthesis progress indicator. Do not treat sending, recognition, playback, or agent generation as one state. See [voice lifecycle](../../../../../docs/VOICE-LIFECYCLE.md) before changing interruption or turn-taking.
Experimental Attendee models keep a bounded host lease and independent participant PCM meters. Dynamic UUID sources reuse MeetingController policy and recording-owned recognition; receiver stop removes source state. AttendeeClient seals sparse bursts on packet-idle, waits for previous STT before restarting, and invalidates on conversation changes. Names never serve as identity. API discovery populates the composer participant list before PCM arrives; connection-local aliases override refreshed names for future text. Participant names are visible between the source icon and wave, with ellipsis and full accessible names. New captures snapshot provider/group/participant identity, original name and alias at begin; later aliases never relabel history. The compact URL-only form submits text Connect or Enter with a pending-request guard, using the persisted Settings name and host-saved key. It explicitly prepares reception before one join request, never on mount. No name override, credential form, configuration icon or local dialog exists in the composer. Save/Replace/Remove key actions belong only to advanced Settings and never start reception. Origin-keyed metadata is boolean-only, never prefills the password, and cannot enable Connect using stale responses. Confirmed credential removal does not revoke a current bot lease or imply departure. The quick form never mounts the key or idle receiver status. Explicit join/leave requests are owner-capability guarded. An uncertain join locks retries on that lease, since an API timeout can already have created a bot. Receiver generations own only PCM/STT; separate owner-guarded bot control survives receiver failure, explicit disconnect and chat navigation. One memory-only host control lease expires after five idle minutes (10-second heartbeat), with a two-hour absolute cap; expiry/release/final disposal never call leave or imply the bot has ended. Late creation updates its original control identity even after receiver stop. Explicit leave failure retains retry; successful leave reports only the last confirmed upstream state. AttendeeClient exposes hasBotControl, botId, botState, leaving, controlExpiresAt and machine-coded controlError separately from active/starting/error, and provides stop, leave, releaseControl and idempotent dispose. UI translates codes but exposes only disconnectMeeting, without confirmation or discard: local state resets immediately and restores the URL form, while bounded remote failure is a nonblocking idle warning; MeetingController.dispose performs final control disposal, while end/stop preserve remote control. See the Attendee guide for upstream overlap and timestamp limitations.
