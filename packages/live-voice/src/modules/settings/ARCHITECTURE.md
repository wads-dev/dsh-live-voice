# Settings module

`services/pluginUpdate.ts` owns an application-lifetime explicit update state machine, passed into Settings by the app composition root. Opening Settings only checks GitHub; Update now reads profile eligibility, then requires a separate exact-version confirmation before the official DSH manager installs. Development/custom sources are never replaced; uncertain outcomes lock retries until the person checks the manager. Closing Settings preserves operation state. Installation never grants build-script permissions or restarts/reloads automatically. Classify structured manager failures for blocked scripts, unavailable versions (including possible publication/release-age delays), and incompatible DSH versions; do not infer a successful update from installed files alone. The three-hour GitHub detection cache is independent of installation and remains unchanged. The inspected DSH manager returns restart-required for existing profile dependencies, so the running plugin is not replaced during download. Voice activity is checked immediately before submission, not reserved across the download or across browser clients. The manager offers no expected-source/CAS option: do not change this dependency through another manager/CLI concurrently with confirmation. Source is rechecked at confirmation but cannot be atomically guarded by this client.

`services/debuggerInstall.ts` owns the separate application-lifetime, explicitly confirmed installation of the matching-version optional debugger through the same remote DSH manager. It rechecks inventory and voice activity before submission and refuses every existing debugger dependency, including disabled registry installs and unreadable custom sources. Submitted failures or uncertain replies lock retries for manager review. The manager has no expected-source/CAS option: do not change the debugger through another manager or CLI during confirmation/installation. `components/DebuggerLauncher.tsx` keeps Diagnostics in the fixed footer without importing the debugger bundle, explains the dependency in a native accessible dialog, and observes the versioned developer-extension registration before reporting ready. An applied result alone is not proof of browser readiness; restart-required results are shown truthfully without restarting or reloading. Dialog styles are feature-scoped.

`components/LiveVoiceSettings.tsx` owns the tabbed Settings shell; `sections/{conversation,recognition,speak}` own feature controls. `hooks/useLiveVoiceSettings.ts` subscribes to controller state and dispatches updates, while `hooks/useAudioDevices.ts` and `hooks/useReleaseStatus.ts` handle capability-adjacent data. `models/settingsStorage.ts` owns the authenticated client transport and in-memory preferences; `models/settingsHost.ts` owns serialized, atomic host-side persistence; `services/releases.ts` supports version metadata. Shared fields, layout, icons, and feedback live in `src/shared/design-system`.

Meeting mode belongs to the Conversation tab, not recognition-engine setup. `conversation/components/AttendeeControls.tsx` exports separate `AttendeeSettings` and operational controls: Settings owns the local API origin, advanced receiver settings in collapsed subcards, and the default bot name directly in the Meeting mode section, regardless of connection state or preferred source. Advanced Settings alone mounts `AttendeeConnectionSettings` with origin/key Save/Replace/Remove. It never starts/stops a receiver. The composer contains only URL and text Connect, using the saved bot name/key through connectMeeting; no local configuration dialog or name override exists. Credentials never enter `updateSettings` or browser storage. Explicit Save/Replace stores typed keys in the exact-origin host credential file; the composer Connect uses the saved key without reading it back. The password field is always initially empty and metadata exposes only key presence. Removing a saved key requires confirmation, can run while reception/control is active and never implies Leave or revokes the current in-memory lease. The file is plaintext 0600, not an OS keychain, shared by authenticated browsers of the same host. An origin-keyed form resets the draft and unresolved metadata immediately, blocks Connect until the current origin resolves, and rejects late responses after remount/unmount. Closing unmounts the key draft without disposing the shared client. The compact composer form owns URL and explicit text/Enter Connect; participants/aliases and departure controls remain in the composer. The persisted Settings name is the only bot-name source. The explicit URL/Connect operation prepares reception and requests one bot; saving Settings never creates a bot. The application-owned client preserves connection-local participants and control across panel mounts. Aliases affect future text without rewriting drafts. The single Disconnect meeting action resets local reception/control and returns to URL + Connect immediately, without a confirmation or discard UI. Remote departure/release is bounded; an unconfirmed result is a nonblocking idle warning and never hides the form. Saved Settings credentials and name remain unchanged.

## Stable preference contract

`models/settingsHost.ts` stores a raw JSON object; it must not import field definitions, `normalizeSettings`, or engine-default policy from the client. The authenticated `GET`/`PUT` route remains `/api/dsh-live-voice/settings`, with the existing `{ ok: true, value, hostPlatform }` success envelope. A missing preferences file returns `{}`. `PUT` merges supplied top-level keys with the latest stored object and returns the complete result. Unknown fields and nested JSON objects/arrays are accepted; each supplied top-level value replaces its predecessor in full, with no recursive merge. No field allowlist, per-field coercion, or field-schema migration belongs in the host store or generic transport.

Safety validation is structural, not product policy: require a JSON object, limit JSON to 64,000 bytes and nesting depth to 16, and reject `__proto__`, `constructor`, and `prototype` keys recursively. Validate loaded data, incoming patches, and the merged result before persistence. Serialize load/merge/write operations so concurrent saves retain unrelated top-level keys; write an exclusive temporary file with mode `0600` and atomically rename it to the fixed plugin-owned preferences path. Settings values never grant access to arbitrary files, caller-selected storage paths, DSH configuration, or YAML. Qwen/Whisper provider configuration stores and their routes remain separate.

`models/settingsStorage.ts` owns authenticated generic JSON transport and unknown-field retention. Client-side `../core/settings.ts` supplies defaults and normalizes known fields; the transport combines that interpreted view with raw unknown fields, which remain intact. New speaking-engine defaults use authenticated `hostPlatform` metadata through `../core/engineSelection.ts`; the host store does not materialize platform defaults, and valid saved choices remain unchanged. Keep browser and host dependency graphs separate.

The running backend needs this generic implementation once, including a DSH restart when the plugin manager requires it. A frontend refresh cannot retrofit an old field-normalizing server. After that rollout, frontend-only preference additions require no backend field changes just to save; new routes, provider behavior, or other backend runtime features still require their implementation to load. This contract persists preferences, not active voice/session state or playback recovery after F5.

## Presentation and engine policy

Engine choice is configuration, not operational validation: every STT/TTS option stays selectable without provider health requests. Configuration load/save uses only the authenticated preference/config routes; explicit Test or start/play performs operational validation. Shared `core/engineSelection.ts` determines display order and client-applied defaults for new preferences from authenticated host-platform metadata, never inferring actual support or overwriting valid saved choices. UI discovery refreshes only local voices, capture metadata, and playback-control mechanics.

`models/browserVoiceSelection.ts` owns pure Browser voice ranking and explicit engine-transition defaults. Rank available local voices by the Natural name label, client browser language family, then alphabetical name; this label is a preference hint, not a capability or quality guarantee. UI translation locale and host OS do not select speech language. Only an explicit transition to Browser preselects a discovered Natural voice. Empty discovery keeps the existing preference; subsequent asynchronous capability refreshes re-rank options without retroactively selecting a voice or overwriting manual choices. The selector groups voices by language family using native optgroups, with the browser language first, other languages alphabetically, and unknown language last; within each section Natural voices precede alphabetical names. The preferred Natural voice keeps a localized default suffix independent of the currently selected voice. Grouping does not change transition-default policy. No speech-language setting is changed.

Preserve existing setting names, default values, handlers, and normalization in `../core/settings.ts`; reorganizing presentation must not silently change policy. All explanatory Settings copy belongs in accessible shared `Hint` tooltips, not permanent descriptions or repeated helper lines. Use one heading tooltip for section-wide instructions. Keep transient capability/permission messages and actionable errors visible even when an options section is collapsed. User-facing copy and accessible names belong in all typed catalogs under `src/app/client/i18n`; UI locale does not select recognition or speech language. The preview in `__previewjs__/LiveVoicePreviews.tsx` exercises presentation with a fake controller, not a physical microphone or authenticated DSH runtime. Run `npm test` after changes and check the preview for layout and interaction.
